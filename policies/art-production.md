# Art production policy

Use this policy whenever CEOS generates or integrates production visual assets.

## Ownership and mutation boundary

- Write only project-owned assets/mappings within the locked task boundary.
- Do not modify narrative/gameplay topology, product state schemas, release metadata, or external systems merely to accommodate generated art.
- Preserve accepted project conventions and existing art pipelines when they exist.

## Capability truthfulness

- Web art-direction routes are reasoning/review only. They do not prove that assets were generated, saved, or integrated.
- Actual asset generation must occur through a native image-generation capability or another explicitly authorized image-capable surface.
- If required image generation is unavailable, report `BLOCKED_CAPABILITY`; do not fake completion with prompt text, empty files, placeholders, procedural stand-ins, or claims that a binary asset exists.

## Canon and consistency

- Recurring characters and locations require explicit canonical references before dependent high-volume generation.
- Variants must preserve approved identity anchors unless the product intentionally changes them.
- Treat identity/style drift as a defect when it changes who/where the reader/player perceives, harms continuity, or violates the approved art direction.

## Evidence

Production-art PASS requires evidence of actual generated files and runtime/content integration, not only prompts or manifests. Evidence should include, as applicable:

- art manifest coverage;
- generated file paths and existence;
- runtime mapping/load validation;
- representative rendered captures;
- Web/native visual review results;
- project-native regression gates.

## External and release boundaries

Image generation itself does not grant permission to publish, upload, deploy, buy, submit, or mutate external services. Release/publication/store artwork is out of scope unless explicitly requested.
